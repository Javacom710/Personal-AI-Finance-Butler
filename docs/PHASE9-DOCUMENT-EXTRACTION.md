# Receipt and statement transaction drafts

Built under the standing Phase 9 approval, stacked on monthly period-summary PR #47. This slice accepts receipt or short cash-transaction statement images through the existing Tier 4 `analyzeDocument` capability. Native PDFs and CAS investment trades remain unavailable. The separate owner question about investment-proposal storage/audit linkage is unanswered; the transaction-only database constraint is unchanged.

Inputs use the existing `ChatImage` envelope: one to five PNG/JPEG/WebP images, at most 2 MiB each and 8 MiB combined. Canonical base64, decoded byte limits and MIME/header agreement are checked before orchestration. This is envelope/header validation, not a new image decoder or OCR service. There is no URL fetch or conversion dependency. Original images remain in memory and are never saved in proposals, history or financial records.

The existing document prompt, strict `document_extraction` response schema, output budget and vision/schema gates remain unchanged. One orchestrated request produces at most twenty transaction proposals. Invalid schema fields, numeric/exponent amounts, unsupported investment kinds, filtered/truncated output and tool requests refuse the whole response with errors; no repair loop is added. Missing dates or amounts stay null with field-level errors. Account/category hints are resolved only against the owner's existing records. Low confidence and ambiguity require acknowledgement. A schema-valid extraction is still an unconfirmed interpretation, never a financial fact or proof of completeness.

Text and document interpretations share one atomic staging helper in the existing proposal table. Each document line retains only its structured line payload and normalized draft; response reasoning is not stored. A batch insertion either stages all lines or none, without a transaction spanning model generation. Each line expires after twenty-four hours. All drafts remain reachable through owner-scoped, stable timestamp/UUID pagination, with fifty rows per page and one lookahead row. Malformed page input fails before database access.

Confirmation uses the unchanged transaction-proposal application path: owner reauthorization, explicit confirmation, deterministic validation, the same manual transaction/transfer service, atomic `ai_confirmed` audit and I-10 linkage, expiry and replay protection. Missing/ambiguous fields must be corrected and acknowledged. Extraction itself never writes to the ledger. Transfers stay transfers rather than income/expenses. The review page keeps missing dates blank instead of substituting today.

The authenticated `/ai/documents` page has disabled image controls and generation. Its independently authenticated direct action returns unavailable without loading images, a provider or financial context. No environment flag or fake production endpoint enables it. Actual vision quality, OCR accuracy and completeness remain unverified until Phase 8 approval and reviewed runtime composition. The fake image/provider tests establish transport, refusal and confirmation behavior only.

Validation: **2,194 unit tests across 81 files pass**, including 79 focused document/proposal checks. **33 PostgreSQL integration tests pass** across the new document cases and existing proposal lifecycle, covering exact decimal strings, missing-field correction, acknowledgement, owner/expiry/replay guards, transfer confirmation, I-10, atomic rollback and all fifty-five paged drafts. Typecheck, lint, local Webpack production build and client-secret scan pass. Local Webpack is required by the reused dependency symlink; CI uses an ordinary installation/default build on PostgreSQL 17/18. No database/tool/response schema, existing gate/rule, tier order, baseline prompt, scorer or evaluation suite changed. Scenarios remain blocked by OD-18.
